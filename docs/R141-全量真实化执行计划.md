## 零 文档约定（先读这一节，否则会误解后文）

### 0.1 关于"绝对/100%"这类词

用户的要求是「必须全部解决，不能存在任何的虚假、任何的错误、任何的缺失、任何的遗漏」。

**本计划承诺这件事，但不用「绝对化完整断言」「绝对化完美断言」「绝对化永不再缺断言」「绝对化无遗漏断言」这四个词做承诺。**

原因不是回避，是这三条：

1. **工作区法则（AGENTS.md 完整性治理条款第 1 条）明令禁止这些词出现在任何输出中**；
2. 这类词**不可验证**——没有任何命令能输出"我绝对化完整断言"；
3. **可验证的判据才是真承诺**。说"绝对化完美断言"谁都能说；说"927 条算法逐条按 inputSchema 真调、每条输出过非空断言、命令可复跑"才有人能查。

**因此本计划用「达成判据」替代「绝对承诺」**：
每一条修复都写明「用什么命令验证、期望什么输出、不满足怎么办」。全部判据通过 = 达到用户要求；任一判据不通过 = 未达到，继续修。

**这不是降低标准，是把标准变成可以被别人检查的东西。**

### 0.2 达成判据的三层定义

任何一条能力，必须**三层全部满足**才算"真实、有效、可用"：

| 层 | 名称 | 判据 | 反例（本次踩到的） |
|---|---|---|---|
| L-1 | **存在层** | 文件/工具/条目存在，能被列出 | 工具在列表里、`--help` 有输出 |
| L-2 | **调用层** | 按声明的 schema 传入**合法参数**，返回**非错误** | `is_superconductive({couplingScore:1.08})` 崩 → L-1 过、L-2 不过 |
| L-3 | **语义层** | 返回内容**与输入的数学/业务关系一致**，非空壳、非回显 | `build_coupling_matrix` 返回 `matrix: []` 却 `success:true` → L-2 过、L-3 不过 |

**本次审计的全部问题，本质都是「只验了 L-1，把 L-2/L-3 当成 L-1」造成的。**

后续所有验证必须显式标注验到第几层。

### 0.3 本计划的验收方式

用户审核本计划 → 批准后执行 → 执行完提交《R141 执行报告》→ 报告里每一条都附：
- 修改前的失败证据（命令 + 原始输出）
- 修改后的通过证据（同一条命令 + 原始输出）
- 回归守卫位置（哪一行、判什么）

**禁止在报告里写"已修复"而不附前后对比证据。**

### 3.1 P0-A01~A04：MCP L3 工具层参数适配

**现象（合并）：** 30 个 L3 快捷工具中至少 4 个不可用，其中 2 个崩溃、2 个返回空壳且报成功。

**根因（已定位到行）：**
`C:\Users\MetaGO\AppData\Roaming\npm\node_modules\@metago-ai\algorithms\tool-registry.js:249-252`
```js
function createL3Handler(toolName, algorithmId) {
  return async (args) => {

```

**问题实质：** MCP 工具的 schema 声明是**结构化对象**（如 `{couplingScore: number}`），而算法 `inputSchema` 声明的是**另一个形状**（如单个裸数值）。`createL3Handler` 把 MCP 的 args 原样丢给算法，中间的**形状适配层完全缺失**。

**修法（三步，缺一不可）：**

1. **建适配表**：为 30 个 L3 工具逐个写明「MCP schema → 算法 inputSchema」的映射规则

   - 多参型：按位置/名称映射
2. **改 `createL3Handler`**：插入适配层，改成
   ```js
   const input = adapter(toolName, args);   // 形状适配
   const result = registry.executeAlgorithmSync(algorithmId, input);
   ```
3. **补输出守卫**：若算法返回空壳而 `success !== false`，必须降级为 `success:false` 并说明原因（禁止空壳报成功）

**验证判据（必须全部满足才算修好）：**

## 四 P1 修复（4 条）

### 4.1 P1-B01：函数型形参桥接

**现象：** `scoreFn: "x => x*2"` 传入后算法收到字符串，无法调用 → 空矩阵。

**根因：** 引擎/适配层未把「表达式字符串」编译为函数。AGENTS.md 附录声称支持 `"x => x*2"` 与 `{"__fn__": "..."}` 两种写法，**实测均不生效**。

**修法：**
1. 在引擎的入参预处理里加一层：形参声明为函数类型时，若收到 string 或 `{__fn__}`，用 `new Function('return ' + src)()` 编译
2. 编译失败必须 `success:false`，禁止静默降级
3. 编译后的函数调用若抛错，必须捕获并转为明确错误

**验证判据：**
```
① execute_sync(ALG_T1_C_019, {labels:[1,2,3], scoreFn:"x => x*2"}) → matrix 非空
② execute_sync(ALG_T1_C_019, {labels:[1,2,3], scoreFn:{"__fn__":"x => x*2"}}) → 同上
③ execute_sync(ALG_T1_C_019, {labels:[1,2,3], scoreFn:"这不是函数"}) → success:false + 明确错误
④ 全量 432 条"函数型形参"算法逐个测（先扫出有多少条属此类）
```

**回归守卫：** 重写 `t3impl/fn-params-test.cjs`——判据从 `success===true` 改为「输出非空 且 与手工计算的期望值一致」。

**风险：** `new Function` 有安全含义（等价 eval）。**限制：仅在本地算法引擎内使用，且只接受形参声明为函数的槽位，不接受任意输入执行。**

### 4.3 P1-B03/B04：检测器判据加固

**现象：** 两个检测器只判"没崩"，让 4 个坏工具 + 1 个失效桥接全部漏过。

**修法（对每个检测器）：**
1. `mcp-tools-callable.cjs`：判据从 `isError` 升级为
   ```
   isError === false
   && result.success !== false
   && 输出不是空对象/空数组（除非输入本身为空）
   && 输出中无 NaN / Infinity / undefined
   ```
2. `fn-params-test.cjs`：判据从 `success` 升级为「输出与期望值逐项比对」
3. **新增检测器自检**：每个检测器必须自带一个"故意造错"的用例——把答案改坏，检测器必须报 FAIL。**检测器抓不到已知错误的，本身判 FAIL。**

**验证判据：**
```
① 用当前这 4 个坏工具喂新检测器 → 必须报 4 条 FAIL（证明有牙）
② 修好后重跑 → 必须全 PASS
③ 检测器自检用例：故意注入 1 个坏值 → 检测器必须 FAIL
```

**这是本轮最重要的一条——它保证以后同类问题不会再被漏过。**

## 十三 达成判据汇总（这一节就是"确保全量完成"的机制）

### 13.1 为什么这个机制能保证"一次性全量完成"

**不能靠"我记得要做完"——要靠"没做完就过不去"。**

本计划用四道机制保证不漏：

| 机制 | 作用 | 不满足会怎样 |
|---|---|---|
| **① 出口条件闸** | 每批出口条件不满足禁止进下一批 | 卡住，无法前进 |
| **② 回归单调闸** | 通过项数必须单调不减 | 回归变红，立即暴露 |
| **③ 检测器有牙闸** | 每个检测器必须能抓住已知错误 | 检测器自身 FAIL |
| **④ 总账清零闸** | 25 项必须全关闭才允许提交报告 | 报告无法完成 |

### 13.2 最终达成判据（逐条可验）

```
G1 无虚假  →  全盘扫"陈述 vs 实测"，不匹配数 = 0
G2 无错误  →  162 工具 + 927 算法 × 2 路径 + 597 原子 + 112 技能
              + 35 智能体 + 8 prompts + 11 CLI + 3 形态，错误数 = 0
G3 无缺失  →  每类能力：声明清单 − 实现清单 = ∅
G4 无遗漏  →  25 项总账全关闭 + 扫描矩阵 S1–S5 全过或已登记
G5 不引入新问题 → 全量回归通过项数 ≥ 37 且单调不减，最终 ≥ 46
```

### 13.3 如果修不好怎么办（诚实条款）

**某些修复可能遇到真实技术障碍**（如 vendor 代码不可改、外部依赖无法伪造）。届时的处置顺序：

1. **能修的必须修**（这是默认）
2. 修不了的 → **必须在法则与报告中明确写为"当前不支持"**，并说明原因与替代路径
3. **禁止把"修不了"写成"已支持"**——这比不修更严重（本次审计的第一类问题就是这个）

**"诚实的不支持"是可接受的终态；"虚假的支持"不可接受。**
