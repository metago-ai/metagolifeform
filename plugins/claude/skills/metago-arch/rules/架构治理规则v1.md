# 架构治理规则 v1.1.0

> 本文件是 SOLID 原则与整洁架构的**可执行规则**，供人和 AI Agent 共同遵守。
> 配套技能：metago-arch ｜ 检查器：`metago-lifeform arch check`（独立安装包：`metago-arch check`）｜ 规则来源：《SOLID与整洁架构全面调研报告》

## 0. 核心心法

业务逻辑是王，数据库/框架/UI 都是随时可换的"细节"。依赖只能向内，接口属于调用方，实现属于被调用方。

## 1. 项目分档（决定检查强度）

| 档位 | 适用 | 强制要求 |
|---|---|---|
| A | 核心产品（长期迭代、多模块、多智能体协作） | 四层整洁架构 + 依赖规则 + 组合根 + 交付前必须 `metago-arch check` |
| B | 中小项目/内部工具 | SOLID 的 S+D+OCP + 简单分层 + 交付前必须 `metago-arch check` |
| C | 脚本/原型/一次性任务 | 不强制检查（`metago-arch init --tier=C` 即跳过） |

档位写在项目根目录 `arch.config.json`：

```json
{
  "tier": "B",
  "check": {
    "strict": true,
    "layers": {
      "domain": ["domain", "entities", "models"],
      "application": ["application", "services", "use-cases", "usecases"],
      "adapters": ["adapters", "api", "controllers", "endpoints"],
      "infrastructure": ["infrastructure", "core", "db", "database"]
    },
    "bannedDeps": {
      "python": ["sqlalchemy", "asyncpg", "httpx", "requests", "redis", "fastapi", "flask", "django", "aiohttp"],
      "ts": ["express", "sequelize", "prisma", "typeorm", "pg", "mysql", "redis", "axios"]
    },
    "allowImports": ["app.core.config", "app.core.database"]
  }
}
```

## 2. SOLID 落地规则

- **S 单一职责**：一个类只有一个变更理由。认证/邮件/存储必须拆开。
- **O 开闭**：加功能用新增代码，不修改已有代码；用接口/多态替代 if-else 分支。
- **L 里氏替换**：子类/实现必须能无缝替换抽象；做不到就拆抽象。
- **I 接口隔离**：按角色拆小接口；禁止"实现一个永远抛异常的方法"。
- **D 依赖倒置**：跨模块调用一律走接口；接口定义权归调用方（高层），实现归被调用方（低层）。

## 3. 整洁架构与依赖规则

四层（从内到外）：

1. **domain（实体）**：核心业务规则，零依赖；
2. **application（用例）**：应用业务逻辑，只依赖 domain 与自身接口；
3. **adapters（接口适配器）**：Controller / Presenter / Repository 实现；
4. **infrastructure（框架与驱动）**：数据库连接、Web 框架装配、组合根。

依赖规则（检查器自动执行，Python 绝对导入同样参与检查）：

- **D1**：domain 层禁止引用 application / adapters / infrastructure（依赖只能向内）；
- **D2**：application 层禁止引用 adapters / infrastructure；
- **D3**：domain 层禁止引用分层外文件（保持自包含）；
- **D4**：domain / application 禁止 import 框架与数据访问库。清单按语言分：Python（sqlalchemy/asyncpg/httpx/requests/redis/fastapi/flask/django/aiohttp 等）、TS/JS（express/sequelize/prisma/pg/mysql/redis/axios 等）。

### 3.1 层映射（真实项目适配）

真实项目常用传统目录（services/models/api/core），没有四层目录名。在 `arch.config.json` 的 `check.layers` 中把真实目录映射到层即可让规则生效（与内置默认合并）：

- `services / use-cases / handlers` → application；
- `models / entities` → domain（若模型是纯业务对象）；
- `api / controllers / endpoints` → adapters；
- `core / db / infrastructure` → infrastructure。

### 3.2 白名单（防误报）

`check.allowImports` 中的模块名（精确或前缀，如 `app.core.config`）在跨层/禁入判定中被豁免，用于配置、DI、组合根等合法场景。豁免时在报告中说明理由。

## 4. 命名规范

- **N1**：用例名是"人类动作"（`PlaceOrder`、`RegisterUser`、`TransferMoney`）；禁止以 `insert/update/delete/remove` 开头（`InsertOrderRecord` 这类数据库操作名是违规）。
- 实体与用例的规则归属：实体管自身约束（"订单最多 50 项"）；用例管跨实体流程（"被封禁用户不能下单"）。

## 5. 跨层数据

- 跨边界传简单独立的数据结构（DTO / 普通对象 / 参数）；
- 禁止把数据库行、ORM 实体、框架对象传进内层；
- 数据格式以"内层方便"为准，外层负责转换。

## 6. 禁止清单（反面示例）

- 用例/业务层里写 SQL / HTTP / Redis 调用；
- domain / application import ORM 或框架；
- 用 `InsertOrderRecord`、`UpdateUserTable`、`SendHttpRequest` 命名用例；
- 只有目录长得像整洁架构，实际依赖箭头乱指；
- 小项目（C 档）强行套四层；
- 分层覆盖率为 0 却宣称"检查通过"（虚假安全感）。

## 7. 目录模板（A 档）

```
src/
├─ domain/entities/          # 实体 + 领域规则
├─ application/use-cases/    # 用例（一个用例一个类）
├─ application/ports/        # 输出端口（presenter / repository 接口）
├─ adapters/controllers/     # HTTP 控制器
├─ adapters/repositories/    # Repository 实现
├─ infrastructure/           # 数据库 / Web 框架 / 配置
└─ main.ts                   # 组合根（注入所有实现）
```

生成命令：`metago-arch scaffold <项目名> --tier=A`

## 8. AI Agent 交付前检查清单

1. 项目档位已配置（arch.config.json 存在）；
2. A/B 档已运行 `metago-arch check <目录>` 且 PASS；
3. 检查报告含**分层覆盖率**（covered/scanned）；strict 模式下覆盖率为 0 = FAIL，禁止宣告通过；
4. 无法立即修复的违规 → 明确标注"已知风险"并说明理由；
5. 未配置档位的新项目默认按 C 档处理（不误伤脚本）；
6. 真实项目用传统目录时，先配置 `check.layers` 层映射再检查。

## 9. 豁免流程

- 需要豁免某条规则或某条导入时，在交付报告中写：规则编号 + 文件 + 理由 + 期限；
- 豁免不代表删除规则；到期后复查。

## 10. 维护

- 本规则每季度复审一次；技术栈变化时更新 D4 禁入清单（python/ts 两套）；
- 规则升级走安装包版本（v1.0.0 → v1.1.0），不手工改已安装文件；
- 试点发现的新盲区（如前端 app router 无业务层、ORM 模型归属争议）持续纳入版本评审。
